# 성적 되돌리기 — 설계 (3단계)

## 배경

2단계(성적 활동 로그, 완료·배포됨: `docs/superpowers/specs/2026-07-26-score-activity-log-design.md`)로
성적 저장/지우기/복사가 언제 누구에 의해 일어났는지는 알 수 있게 됐다. 하지만 지금 로그 항목은
"무슨 일이 있었다"는 요약(인원수·누가·언제)만 담고 있어서, 실수로 지우거나 잘못 복사했을 때 그
전 상태로 되돌릴 방법이 없다. 이 설계는 3단계로 예정된 작업의 마지막 단계다:
1. 조교 다중 계정 (완료)
2. 성적 활동 로그 (완료)
3. **되돌리기** (이 문서의 범위)

## 확정된 요구사항

성적 저장(일괄 입력)·이번 주 성적 지우기·다른 주차로 복사, 세 행동 모두 되돌리기 대상에 포함한다
(저장도 포함 — 사용자가 명시적으로 확인).

## 핵심 설계 결정: 행동 직전 스냅샷을 로그에 함께 저장

로그 항목에 "그 행동으로 바뀐 학생들의, 바뀌기 **직전** 입력값"을 통째로 저장해둬야 되돌릴 수 있다.
세 행동 모두 저장 직전(`saveDB` 호출 전)에 영향받는 학생들의 레코드를 스냅샷으로 만들어 로그
항목에 실어 보낸다.

### 스냅샷에 무엇을 담는가 — "입력 필드"만, "계산 필드"는 제외

레코드에는 두 종류의 필드가 있다:
- **입력 필드**: `thrRt, thrWt, rtSkip, rtScore, wtSkip, wtScore, hw1, hw2, homework, hwName1,
  hwName2, retestTime, comment, attendType` — 사람이 직접 입력하거나 UI에서 고른 값. 이건
  스냅샷에 담아 그대로 복원해야 한다.
- **계산 필드**: `totalScore, rvRank, wtRank, totalRank, rtPass, wtPass, rvAvg, wtAvg, totalAvg`
  — 기존 `recomputeWeekAggregates(sc,mon,week)`가 그 주차 전체 데이터를 기준으로 다시 계산해주는
  값. 되돌리기 후에도 이 함수를 다시 호출하면 자동으로 올바르게 채워지므로, 스냅샷에 담을 필요가
  없다. (오히려 스냅샷 시점의 계산값을 그대로 복원하면, 그 사이 다른 학생 데이터가 바뀐 경우
  등수·반평균이 실제 현재 데이터와 안 맞게 될 위험이 있다 — 계산 필드는 항상 "지금 데이터 기준으로
  다시 계산"하는 쪽이 안전하다.)

스냅샷 형태(학생별 하나씩):
```js
{ sid, wasNew: boolean, fields: { thrRt, thrWt, rtSkip, rtScore, wtSkip, wtScore, hw1, hw2,
  homework, hwName1, hwName2, retestTime, comment, attendType } }
```
`wasNew:true`는 "이 행동 이전엔 그 학생의 그 주차 레코드 자체가 없었다"는 뜻 — 되돌릴 때 값을
복원하는 게 아니라 레코드 자체를 삭제해야 한다는 신호로 쓴다.

**스냅샷 범위는 로그의 `count`(화면에 보여주는, "의미 있게 값이 있던 인원수")와 다를 수 있다** —
스냅샷은 항상 그 행동이 **실제로 mutate하는 레코드 전체**를 담아야 완전한 되돌리기가 된다. 예를
들어 "지우기"의 `count`는 지우기 전에 실제 값이 있던 학생 수만 세지만(사용자에게 보여줄 때
의미 있는 숫자라서), 코드는 그 주차의 **모든** 레코드를 지운다(이미 비어있던 레코드도 포함) — 그러니
스냅샷도 `count`가 아니라 그 주차 레코드 **전체**를 대상으로 떠야 한다.

### 각 행동에서 스냅샷을 뜨는 시점

- **성적 일괄 저장** (`btn-save` 핸들러): 각 학생의 기존 레코드를 새 `rec`으로 덮어쓰기(또는
  push)하기 **직전**에, 기존 레코드가 있으면 그 입력 필드를, 없으면 `wasNew:true`를 기록. 대상은
  `rows`(그 주차 입력 화면에 보이는 학생 전체) — 이미 `savedSids`가 이 전체 집합이므로 스냅샷
  범위와 `count`가 일치한다.
- **이번 주 성적 지우기** (`clearWeekScores`): 필드를 `null`/`''`로 지우기 **직전**에, `wkRecs`
  (그 주차의 **모든** 레코드 — 지우기 전 값이 있었든 없었든 전부, `clearedCount`로 필터링하기
  **전** 배열)의 현재 입력 필드값을 기록(레코드 자체는 원래도 존재했으므로 `wasNew`는 항상 false).
  로그의 `count`는 기존대로 `clearedCount`(값이 있던 인원수)를 그대로 쓰되, `snapshot` 배열은
  `wkRecs` 전체 길이가 된다 — 되돌리기는 `snapshot`을 기준으로 동작하므로 항상 완전하게 복원된다.
- **다른 주차로 복사** (`copyWeekTo`): 대상(도착지) 주차의 기존 레코드를 `Object.assign`으로
  덮어쓰기 **직전**에, 대상 레코드가 있으면 그 입력 필드를, 없으면 `wasNew:true`를 기록(원본
  주차는 건드리지 않으므로 스냅샷 대상이 아님). 대상은 `srcRecs` 전체이며 `count:srcRecs.length`와
  스냅샷 범위가 일치한다.

## 되돌리기 실행

새 함수 `undoActionLog(sc, entry)`:
1. `entry.snapshot`의 각 항목에 대해: `wasNew`면 해당 `sid`의 레코드를 `sc.records`에서 제거,
   아니면 해당 레코드의 입력 필드를 스냅샷 값으로 복원(레코드가 어떤 이유로 이미 없어졌다면
   방어적으로 새로 만들어 복원).
2. `recomputeWeekAggregates(sc, entry.month, entry.week)`로 그 주차 전체의 계산 필드를 다시 계산.
3. 영향받은 `sid`들로 `dirtyKeys`를 만들어 `saveDB({dirtyKeys})` 호출 — 1단계에서 검증된 낙관적
   락 merge 로직을 그대로 재사용(새 저장/충돌 처리 로직 불필요).
4. `addActionLog(sc, {type:'undo', month:entry.month, week:entry.week, count:entry.snapshot.length,
   undoneLogId: entry.id})`로 "되돌리기" 자체도 로그에 남김 — 스냅샷은 없음(되돌리기는 다시
   되돌릴 수 없음, YAGNI로 명시적으로 범위 밖).

## 로그 항목에 고유 id 추가

지금 로그 항목은 배열에 순서대로 쌓일 뿐 안정적인 식별자가 없다. "이 항목을 되돌렸다"를 표시하고
"이 항목은 이미 되돌려졌다"를 판단하려면 각 항목에 고유 `id`가 있어야 한다. `pushLogEntry`(2단계에서
추가됨)가 항목을 만들 때 `id: crypto.randomUUID?crypto.randomUUID():(Date.now()+'-'+Math.random().toString(36).slice(2,10))`로
채운다 — 조교 여러 명이 동시에 로그를 남겨도 충돌하지 않도록(1단계 사건과 같은 동시성 상황에서도
안전).

## "이미 되돌려졌는가"는 저장하지 않고, 매번 로그 전체에서 유추한다

기존 로그 항목을 직접 수정(`undone:true` 같은 플래그를 나중에 써넣는 것)하려면 새 서버 API가
필요하다 — 지금 서버는 `append-save-log`로 로그를 **추가만** 할 수 있고, 학교 전체 PUT은
`saveLogs` 필드를 클라이언트 값으로 절대 덮어쓰지 않도록 서버가 이미 막아뒀다(2단계 최종 검토에서
확인된 안전장치, `normalizeSchoolForWrite`). 그래서 로그를 "추가 전용 기록"으로 그대로 유지하고,
대신 화면에서 "이 항목이 이미 되돌려졌는지"를 **매번 계산**한다:
```js
const isUndone = (entryId) => logs.some(e => e.type==='undo' && e.undoneLogId === entryId);
```
이러면 새 서버 API가 전혀 필요 없다 — 기존 `append-save-log` 하나로 저장/지우기/복사/되돌리기
전부 처리된다.

## 화면 (`rLogs`)

- `type`이 `'save'`/`'clear'`/`'copy'`이고, `entry.snapshot`이 있고(하위호환: 이 기능 배포 전
  로그는 스냅샷이 없으므로 버튼 자체를 숨김), 아직 되돌려지지 않은 항목에만 "되돌리기" 버튼 표시.
- 이미 되돌려진 항목은 버튼 대신 "되돌려짐" 표시로 바뀜.
- `type==='undo'` 항목 자체에는 되돌리기 버튼이 없음(스냅샷이 없으므로 애초에 대상이 아님) — 대신
  "OOO님이 △△△님의 [원래 행동]을 되돌림" 형태로 표시해 감사에 도움.
- 되돌리기 버튼 클릭 시 확인창: "N명의 [저장/지우기/복사] 내용을 [스냅샷 시각] 상태로 되돌립니다.
  그 이후 이 주차에 다른 변경이 있었다면 그 변경도 함께 사라질 수 있습니다. 계속하시겠습니까?"
  — 시점 사이 다른 변경 가능성을 명시적으로 경고(별도 감지 로직은 만들지 않음, YAGNI).

## 보관 정책

기존과 동일하게 최근 200건(2단계 그대로). 스냅샷이 붙어 로그 항목 크기가 커지지만, 학교 규모(수십
명 단위)에서 200건 기준 용량 문제는 없을 것으로 판단 — 실제로 문제가 되면 이후 조정.

## 이번 단계에서 하지 않는 것 (YAGNI)

- 되돌리기 자체를 다시 되돌리는 기능(redo) — undo 항목은 스냅샷을 갖지 않음
- 시간 제한이 있는 "되돌리기 가능 기간" — 로그에 있는 어떤 항목이든 항상 되돌릴 수 있음(대신
  확인창에 경고 문구로 위험을 알림)
- 스냅샷 시점 이후 실제로 다른 변경이 있었는지 자동 감지/차단 — 확인창 경고 문구로 충분하다고
  판단
- 성적 외 다른 행동(조교 계정 관리 등)의 되돌리기

## 검증 계획

- 배포 후 로컬 문법 검사(`node -e` + 기존 `<script>` 줄 번호 확인 관례) 통과 확인
- 실제 마스터 계정으로 로그인 → 성적 일괄 저장 → 되돌리기 → 스냅샷 이전 값으로 정확히 복원되는지,
  등수·반평균이 다시 정상 계산되는지 확인
- "이번 주 성적 지우기" → 되돌리기 → 지우기 전 값이 정확히 복원되는지 확인
- "다른 주차로 복사"(기존에 그 주차에 값이 있던 상태에서 복사) → 되돌리기 → 복사로 덮어써진 원래
  값이 정확히 복원되는지 확인
- 원래 레코드가 없던 학생에게 처음 저장/복사한 경우 → 되돌리기 → 레코드 자체가 삭제되는지(값이
  빈 걸로 남지 않고) 확인
- 같은 로그 항목을 두 번 되돌리려고 시도 → 버튼이 이미 "되돌려짐"으로 바뀌어 재실행이 안 되는지 확인
- 옛날 로그(스냅샷 없음, 2단계 이전 데이터)에는 되돌리기 버튼이 아예 안 뜨는지 확인
- 조교 계정으로도 되돌리기 실행 → 로그에 되돌린 사람 이름이 정확히 남는지 확인
